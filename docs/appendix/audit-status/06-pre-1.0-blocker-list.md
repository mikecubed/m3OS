# 06 — Pre-1.0 Blocker List

This document is the actionable summary. It enumerates the items that, in the auditor's view, would need to close before m3OS can credibly claim a 1.0 release — or before the project should claim that the items in question are "done".

The list is grouped by category. Each item has:

- **Severity** — 🛑 critical / 🔴 high / 🟠 medium / 🟡 low (cosmetic but impactful)
- **Effort** — rough estimate (mins / hours / days / weeks)
- **Owner** — current owner phase if any (or "unassigned" if none)
- **Source** — citation back to `findings/*.md` or other audit doc

This is the auditor's recommendation, not project policy. The project may decide some items are not actually 1.0 blockers and should ship as documented limitations — but in that case, the documentation should match.

## E. Code-side architectural items

These are architectural shortcuts that should at least be acknowledged in the README's known-limitations section.

### E1. 🛑 W^X is absent
**Status:** All userspace code pages are mapped writable. `kernel/src/mm/user_space.rs:135, 143`.
**Effort:** Multi-week. Touches the page-table walker and ELF loader.
**Owner:** unassigned.
**Source:** Audit § Code-side architectural deferrals.

### E2. 🛑 IPC capability grants, bulk transfers, and timeouts are absent
**Status:** Documented as "Phase 7+ deferred" in `kernel/src/ipc/mod.rs:34-35`. These are foundational seL4-style features.
**Effort:** Multi-month — comparable to a major phase.
**Owner:** unassigned. Phase 50 was named "IPC Completion" but did not deliver these.
**Source:** Audit § Phase 50, Code-side architectural deferrals.

### E3. 🟠 VT-d scalable mode and queued invalidation disabled
**Status:** Permanent limitations on modern VT-d hardware.
**Effort:** 1 week each.
**Owner:** Phase 55a successor.
**Source:** Audit § Phase 55a.

### E4. 🟠 Triple-indirect ext2 reads return `CorruptedEntry` not `ENOSYS`/`EFBIG`
**Status:** Files >~8 MB silently appear corrupt.
**Effort:** 1 hour to change error code; 1 week to actually implement.
**Source:** Audit § Phase 28.

### E5. 🟡 PCI BAR PAT slot management absent
**Status:** Blanket `NO_CACHE | WRITE_THROUGH` for all BAR MMIO.
**Effort:** 1 week.
**Source:** Audit § Code-side.

### E6. 🟡 Unsafe-block SAFETY-comment coverage at ~59% in kernel
**Status:** ~217 unsafe blocks lack adjacent rationale; concentrated in `syscall/mod.rs`, `interrupts.rs`, `scheduler.rs`.
**Effort:** Ongoing — 1 day per file is a reasonable baseline.
**Source:** Audit § Code-side.

### E7. 🟡 Three deprecated termios register-return ABI surfaces retained on both sides
**Status:** Dead ABI surface; no in-tree caller after Phase 52d.
**Effort:** 1 day to remove syscall + userspace wrappers.
**Source:** Audit § Code-side.

### E8. 🟡 14 preemption + XSAVE tests are all `#[ignore]`d, blocked on "Track G activation"
**Status:** Track G is not assigned to a completed or planned phase.
**Effort:** Define Track G as a sub-deliverable of Phase 57e.
**Source:** Audit § Code-side.

## Suggested phase decomposition

If the project commits to a 1.0 release gate, the work above naturally groups into a small number of follow-on phases:

1. **Phase 51 closeout** (A4, A5) — 1–2 days. Pure documentation: write task doc or merge into 52d retrospectively.
2. **Phase 56b — display server completion** (C5, plus damage tracking) — 1 week.
3. **Phase 55d — IOMMU completion** (C7, E3, the AMD-Vi fault ISR + VT-d scalable mode + queued invalidation + multi-BDF AMD-Vi domains) — 2–3 weeks.
4. **Phase 57f — preemption hygiene** (C3, C8, B7, plus the soak/track-G activation) — 1 week. Closes pi_lock wiring, tick-multiplier bugs, soak.
5. **Phase 58 (Release 1.0 Gate) — already on the roadmap.** This audit suggests:
   - The gate cannot honestly close until A1, A2, A3, A4, A5 are reconciled (documentation integrity).
   - The validation runs in section B should be run.
   - C1, C2, C4 (slab migration, load balancing, fat_server) are decisions: implement, accept-as-deferred, or accept-as-removed.
   - E1 (W^X) and E2 (IPC capabilities) are architectural items the 1.0 declaration should acknowledge as known limitations rather than hide.
6. **Doc-cleanup pass** (A6, A7, A8, A9, A10, A11, A12) — 1–2 days. Get the roadmap into a state where the status fields are reliable.

Total recommended pre-1.0 effort: **6–10 weeks of focused work**, plus ongoing reduction of the unsafe-block SAFETY-comment gap (E6) and the bug-doc residuals (section D).
