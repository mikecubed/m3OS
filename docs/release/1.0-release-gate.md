# m3OS 1.0 Release Gate

**Status:** Authoritative release contract
**Source Ref:** phase-83
**Kernel crate version at this gate:** `0.83.0` (phase-tracked — see [Versioning Posture](#versioning-posture); "1.0" is a quality-bar milestone, **not** a SemVer `1.0.0` commitment)
**Companion docs:** [Phase 83 design doc](../roadmap/83-release-1-0-gate.md) · [Phase 83 task list](../roadmap/tasks/83-release-1-0-gate-tasks.md) · [Phase 83 learning doc](../83-release-1-0-gate.md)

This document is the single authoritative statement of what m3OS **promises** at the
1.0 quality bar, **on which targets**, **with which workflows**, and **with which
explicit non-goals** — and the **evidence** (named, reproducible `cargo xtask` gates)
behind every claim. It ships no runtime code: the only source change in Phase 83 is the
`kernel/Cargo.toml` version bump. A capability the matrix would need but that has no
existing gate is recorded as a [non-goal / follow-up](#non-goals-and-known-limitations),
never invented here.

> **Relationship to Phase 53.** This document **extends** — it does **not** replace —
> the Phase 53 [support boundary](../roadmap/53-headless-hardening.md#support-boundary)
> and [gate bundle](../roadmap/53-headless-hardening.md#gate-bundle), which remain the
> headless/reference baseline. It **supersedes** Phase 53's now-stale *Out of scope* rows
> "GUI / display compositor / graphical session" and "Mouse input or audio" — both were
> delivered in Phases 56/57 and are first-class 1.0 rows below. The Phase 53 file is
> footnoted to point here (Phase 83 Track D.6).

## Status Legend

Every cell in the [Support Matrix](#support-matrix) uses **exactly one** of the
following closed status words and nothing else. Free-text such as "works" or
"should work" is disallowed — a support matrix is only honest if its status words are
*defined*. This mirrors seL4's verified-platform table, whose every cell is drawn from a
closed legend rather than prose, so a QEMU-only proof can never be silently presented as
full hardware support.

| Status | Definition |
|---|---|
| `Supported` | A first-class 1.0 promise on the [recommended configuration](#recommended-configuration). Backed by a must-pass gate whose evidence **directly observes the user-facing behavior** — end-to-end serial for headless workflows, a framebuffer **screenshot** for visible claims, a non-silent **WAV** for audible claims. The project commits to keeping it working. |
| `QEMU-validated` | Proven by an automated gate running under **emulated QEMU hardware** (serial- or device-level). The support claim is scoped to the QEMU device model; real silicon is **not** claimed because QEMU's model is known to diverge (e.g. NVMe/AHCI controller behavior). |
| `Host-tested-only` | Logic proven by host-side unit/property tests (`cargo xtask check`), **not** executed inside a booted guest. Used for code whose device cannot be emulated in QEMU. |
| `Bare-metal-validated` | Proven **only on real hardware** (VFIO pass-through on a developer laptop, or a documented bare-metal runbook) because QEMU ships **no** device model for it. Not exercised by CI — the validation method is named per row. |
| `Experimental` | Present in-tree and partially exercised, but **lacking** a dedicated must-pass gate or the observable-output proof its claim requires. **Not** a 1.0 promise. |
| `Out-of-scope` | Explicitly **not** part of the 1.0 promise. Enumerated in [Non-Goals and Known Limitations](#non-goals-and-known-limitations) with a one-line reason. |

The three middle tiers (`QEMU-validated`, `Host-tested-only`, `Bare-metal-validated`)
exist specifically so that QEMU-blind capabilities — the mt76 Wi-Fi radio (no QEMU
model), AHCI hot-plug/BOHC/SSS (no-ops under `ich9-ahci`), and RTL8125 2.5 G silicon —
**cannot** be folded into plain `Supported`.

## Release Scope Decision

**1.0 includes the local-system / graphical branch.** The graphical session
(greeter → login → compositor → `term` / launcher / bar, with USB-HID input and
HDA/AC'97 audio) is a **`Supported`, screenshot-validated** workflow — not deferred to
1.x. **SSH-first / headless remains the recommended *administration* path.**

This resolves the design doc's earlier open headless-vs-local question. The decision is
**recorded with phase evidence**, not merely asserted; the constituent work is complete
in-tree:

| Evidence | Phase |
|---|---|
| First real full-screen graphical workload (DOOM) | [Phase 47](../roadmap/47-doom.md) |
| `display_server` (framebuffer owner) + focus-aware input dispatch | [Phase 56](../roadmap/56-display-and-input-architecture.md) |
| Audio (AC'97 ring-3 driver) + `session_manager` graphical-session orchestrator + `term` | [Phase 57](../roadmap/57-audio-and-local-session.md) |
| USB-HID keyboard/mouse input (xHCI host + HID boot-protocol) | [Phase 78](../roadmap/78-usb-host-foundation.md) |
| Intel HDA audio controller + widget-graph codec | [Phase 80](../roadmap/80-intel-hda-audio.md) |

The graphical branch is a `Supported` *workflow*; the recommended *admin* surface stays
SSH-first because remote administration is the path the project hardens and exercises
most heavily. A full general-purpose **desktop** (broad app ecosystem, window-management
parity) is **out of scope** for 1.0 — see [Non-Goals](#non-goals-and-known-limitations).

## Versioning Posture

**The kernel crate is bumped to `0.83.0` and stays phase-tracked.** "1.0" in this
document is **quality-bar / milestone language**, not a SemVer `1.0.0` crate version.

Per [SemVer 2.0.0](https://semver.org/):

- **Item 4** — *"Major version zero (0.y.z) is for initial development. Anything MAY
  change at any time. The public API SHOULD NOT be considered stable."* This licenses
  m3OS staying on `0.x` while its public syscall/userspace ABI is unfrozen.
- **Item 5** — *"Version 1.0.0 defines the public API."* Declaring `1.0.0` would assert a
  stable public API the system **does not hold and is not ready to make**: it is still
  adding whole subsystems (Wi-Fi landed in [Phase 81](../roadmap/81-wifi-reference-driver.md),
  AHCI in [Phase 82](../roadmap/82-ahci-sata-storage.md)). It would also break the
  `0.NN.0 = Phase NN` mapping the roadmap relies on.

**Precedent.** This mirrors the nearest peers: **Redox** deliberately stays `0.x`, gating
its 1.0 on a frozen [`relibc`](https://gitlab.redox-os.org/redox-os/relibc) ABI;
**SerenityOS** ships **no** numbered release and stays perpetually pre-1.0; **Haiku**
ships "feature-complete" milestones as *beta*.

**The headline blocker for an eventual SemVer `1.0.0`** is a **frozen public
syscall/userspace ABI** — ideally isolated in a narrow, separately versioned
`syscall-abi`-style surface (à la Redox's `relibc`) so the stability promise covers only
what is actually frozen. This is enumerated as the lead item in
[Non-Goals and Known Limitations](#non-goals-and-known-limitations).

> No reference in the tree bumps the kernel crate to `1.0.0`; `grep -r '1\.0\.0'` over
> `kernel/Cargo.toml` finds nothing. "1.0" appears only as milestone/public language.

## System Requirements

Concrete minimums for the machine m3OS is claimed to run on:

| Requirement | Minimum |
|---|---|
| Architecture | **x86_64** (64-bit only) |
| Firmware | **UEFI** (OVMF under QEMU) — **legacy BIOS is not supported** |
| RAM floor | **256 MiB** absolute minimum (the xtask `-m` floor); **2048 MiB recommended** (the default the gate bundle exercises; the graphical path and heap/allocator want the headroom) |
| CPU features | **SSE + XSAVE state handling** — the kernel's BSP CPUID probe (`kernel/src/arch/x86_64/cpuid.rs`) requires **XSAVE/AVX/XSAVEOPT** to enable `CR4.OSXSAVE` + `XCR0` at boot. **SMEP + SMAP** are enforced on every core when the CPU advertises them (CPUID.07h:EBX[7]/[20]). |
| Storage | One block device: VirtIO-blk (reference), NVMe, or AHCI/SATA — root filesystem is **ext2** |

## Recommended Configuration

The single validated "most complete experience" configuration — the exact device set the
[gate bundle](#gate-bundle) actually exercises — is the **q35** machine under **OVMF
(UEFI)** with the Intel **82540EM e1000** NIC, a **VirtIO-blk ext2** root (NVMe and
AHCI/SATA are also `QEMU-validated` storage), the TCG CPU model
`qemu64,+xsave,+avx,+xsaveopt,+smep,+smap` (or `-cpu host` under KVM), **2048 MiB** RAM,
and `-vga std` for the framebuffer.

Reproduce it with the copy-pasteable commands the project ships — no bespoke QEMU
line required:

```bash
# Headless / reference admin path (recommended administration surface)
cargo xtask run

# Local-system / graphical session (greeter → compositor → term/launcher/bar)
cargo xtask run-gui

# Reproducible, signed release image (see Release Checklist)
cargo xtask image --sign
```

Under KVM, append `--kvm` for near-native speed; `cargo xtask run-gui` uses the same q35 +
OVMF + e1000 device set with a framebuffer display.

## Gate Bundle

The gate bundle is the release "definition of done" — it turns the [Support
Matrix](#support-matrix) promise into evidence-backed, repeatable proof. Gates fall into
**two classes**.

**PASS-not-SKIP discipline (the core rule).** A gate whose backing test can **SKIP**
(musl cross-compiler absent → `tls-smoke`/`dns-smoke` SKIP; no QEMU mt76 model →
`wifi-smoke` skip-with-reason) must be run on a platform where it actually **PASSes**
before the corresponding `Supported`/`QEMU-validated` claim is made — **or** the matrix
row is downgraded (e.g. to `Bare-metal-validated`). A SKIP **never** counts as a PASS.
This generalizes the repo's existing `tls-smoke`/`dns-smoke` PASS-not-SKIP rule so a 1.0
claim never rides on unverified, musl-absent, or QEMU-unmodeled paths.

### Class (1) — env-gated opt-in regression gates

These carry a `M3OS_*_REGRESSION` trigger. The env vars below are quoted **verbatim** from
the [AGENTS.md](../../AGENTS.md) opt-in regression gate table (the source of truth) so the
two never drift.

| Gate command | Env trigger | PASS condition |
|---|---|---|
| `cargo xtask ssh-e1000-banner-check` | `M3OS_E1000_REGRESSION=1` | SSH banner observed over the e1000 wake path |
| `cargo xtask doom-audio-smoke` | `M3OS_DOOM_AUDIO_REGRESSION=1` | `AUDIO_DEMO:PASS` + non-silent WAV |
| `cargo xtask termios-smoke` | `M3OS_TERMIOS_REGRESSION=1` | `TC_SMOKE:*:ok` for every termios sub-case |
| `cargo xtask tui-app-smoke` | `M3OS_TUI_APP_REGRESSION=1` | less + htop + tmux smokes pass |
| `cargo xtask doom-concurrent-smoke` | `M3OS_DOOM_CONCURRENT_REGRESSION=1` | both concurrent DOOM instances reach title + exit clean |
| `cargo xtask tiling-smoke` | `M3OS_TILING_REGRESSION=1` | `m3ctl` version/workspace/layout/reload ACKs |
| `cargo xtask htop-render-probe` | `M3OS_HTOP_REGRESSION=1` | htop process-table band changed ≥ threshold scanlines (screenshot) |
| `cargo xtask xhci-bringup-smoke` + `cargo xtask xhci-enum-smoke` + `cargo xtask usb-smoke` | `M3OS_USB_REGRESSION=1` | enable-slot OK + enum configured + USB keystrokes render as glyphs (screenshot) |
| `cargo xtask smoke-test` (`tls-smoke` stage) PASS (not SKIP) | `M3OS_TLS_REGRESSION=1` | musl-built TLS stage PASSes (not SKIP) |
| `cargo xtask smoke-test` (`dns-smoke` stage) PASS (not SKIP) | `M3OS_DNS_REGRESSION=1` | musl-built DNS stage PASSes (not SKIP) |
| `cargo xtask multi-nic-smoke` (e1000 + e1000e + igb arms) | `M3OS_MULTI_NIC_REGRESSION=1` | each enabled NIC arm registers + links |
| `cargo xtask hda-smoke` (`-device intel-hda -device hda-duplex`) | `M3OS_HDA_REGRESSION=1` | non-silent WAV |
| `cargo xtask wifi-smoke` (skip-with-reason; VFIO) | `M3OS_WIFI_REGRESSION=1` | structural skip-with-reason (no QEMU mt76 model); radio PASS only on VFIO |
| `cargo xtask ahci-smoke` + `cargo xtask ahci-root-smoke` | `M3OS_AHCI_REGRESSION=1` | IDENTIFY/RW/flush/recover + root mounts off `ahci.block` |

### Class (2) — always-on / non-env probes

These have **no** `M3OS_*_REGRESSION` var and run on every gate sweep. The verbatim-env-var
check of Class (1) is **never** applied to them. *(Promoting one — e.g. `compositor-stress`

| Gate command | Class | PASS condition |
|---|---|---|

| `cargo xtask compositor-stress` | always-on (screenshot plumbing) | no panic/OOM across workspace + spawn cycles |
| `cargo xtask less-render-probe` | always-on (screenshot) | `less` content renders and does not disappear |
| `cargo xtask session-smoke` | always-on | `session.boot: state=running` (graphical session entry) |

## Hardware-Honesty Tiering

Several capabilities are inherently **un-provable in QEMU**. The matrix must never collapse
host-tested / QEMU-validated / bare-metal into "supported" — that is the "over-claiming
hardware from QEMU alone" anti-pattern. Per-row rules:

- **Wi-Fi (mt792x)** is `Host-tested-only` **and** `Bare-metal-validated`, **never** plain
  `Supported`. The soft-MAC 802.11 FSM and WPA2-PSK 4-way handshake are host-tested
  (`cargo xtask check` over `wifi-core`/`crypto-lib`); the radio itself is validated only
  via **VFIO pass-through on a developer laptop** because **there is no QEMU mt76 device
  model**. `wifi-smoke` is therefore a structural skip-with-reason gate, not a PASS.
- **AHCI hot-plug / BOHC / SSS** and **RTL8125 2.5 G** are `Bare-metal-validated` with their
  QEMU-skip reason inline: QEMU's `ich9-ahci` leaves hot-plug/BOHC/SSS as no-ops, and there
  is no reliable QEMU model for RTL8125 silicon. The AHCI **root-mount + IDENTIFY/RW/flush/
  recover** path *is* `QEMU-validated`, backed by `ahci-smoke` + `ahci-root-smoke`.
- **igc / r8169** likewise are `Bare-metal-validated` (VFIO / real NIC); only the e1000 /
  e1000e / igb arms of `multi-nic-smoke` run under QEMU.
- Every `Bare-metal-validated` row **names its validation method** (VFIO pass-through, or a
  documented real-hardware runbook) rather than implying CI coverage.

## Graphical / Local-System Evidence

The GUI is in 1.0 scope, and the serial-only smoke harness is **blind to rendering** — a
serial sentinel proves a program *ran*, not that it *drew* anything (SerenityOS's CI takes
the same posture: boot under QEMU and assert on framebuffer screenshots). Therefore **every
"the screen shows X" claim is backed by a QMP/PPM screenshot probe**
(`QmpClient::screendump` in `xtask/src/qmp.rs` + `ppm` pixel assertions in
`xtask/src/ppm.rs`), and every audible claim by a non-silent WAV capture — **never** a
serial `Wait` on a sentinel.

The screenshot/WAV-validated set is drawn **only from gates that already exist** — **no gate
is invented** (the no-new-runtime-code rule):

| Graphical / audible row | Backing screenshot/WAV gate | Evidence kind |
|---|---|---|
| Graphical session (compositor + `term`) | `less-render-probe`, `htop-render-probe`, `compositor-stress` | QMP/PPM screenshot |
| Graphical session (tiling) | `tiling-smoke` (+ `compositor-stress` liveness) | `m3ctl` ACK + liveness |
| USB-HID input | `usb-smoke` | QMP/PPM screenshot (typed glyphs) |
| Audio: AC'97 / HDA | `doom-audio-smoke` / `audio-smoke` / `bell-smoke` / `hda-smoke` | non-silent WAV |
| greeter / login render | `session-smoke` + `compositor-stress` | **no dedicated greeter render probe** → `Experimental` |

**The greeter row is `Experimental`, not `Supported`:** xtask ships `session-smoke` and
`compositor-stress` but **no greeter render probe** today. Building one is recorded as an
[A.5 follow-up](#non-goals-and-known-limitations), **not** smuggled into this documentation
phase. Any graphical capability with no screenshot/WAV probe is `Experimental` /
`Host-tested-only`, never `Supported`.

## Non-Goals and Known Limitations

Each item is **specific and bounded** — it names the exact missing capability and a one-line
reason. Vague phrasing such as "not production-ready" is disallowed.

- **No frozen public syscall/userspace ABI.** *(Headline.)* This is the reason 1.0 is a
  quality-bar milestone rather than a SemVer `1.0.0` — see [Versioning
  Posture](#versioning-posture). An eventual `1.0.0` requires freezing the public
  syscall/userspace ABI, ideally in a narrow separately versioned `syscall-abi`-style
  surface (à la Redox's `relibc`).
- **No greeter/login render probe.** The greeter row is `Experimental` until a QMP/PPM
  greeter render gate exists; the screenshot probe is a tracked follow-up.
- **No NCQ** (Native Command Queuing) on the AHCI/SATA driver — single command slot only.
- **No AHCI hot-plug / staggered spin-up (SSS) / BIOS-OS handoff (BOHC)** — QEMU `ich9-ahci`
  leaves these as no-ops; validated only via VFIO.
- **No non-`Sata` AHCI signatures** — ATAPI/port-multiplier signatures are not handled.
- **No QEMU mt76 Wi-Fi model** — the radio is VFIO/bare-metal-only; CI exercises host logic.
- **No IPv6 / DHCPv6** — IPv4 only ([Phase 89](../roadmap/README.md) is post-1.0 1.x scope).
- **No SMP CPU hot-unplug** — cores boot at init; dynamic removal is unsupported.
- **No GPU acceleration** — software framebuffer compositor only.
- **No FAT32 writes** — `fat_server` is a **permanent ENOSYS stub** ([Phase
  65](../roadmap/README.md)); **ext2 is the supported on-disk filesystem**.
- **No full general-purpose desktop** — broad app ecosystem / window-management parity is
  beyond the screenshot-validated greeter → compositor → `term`/launcher/bar session 1.0
  ships.
- **No outbound HTTPS/TLS client tooling, `git`/`gh`, or remote package feeds** as 1.0
  promises (DNS resolution *is* delivered; see Phase 53 boundary).

**Post-1.0 phases are 1.x scope, not 1.0 blockers:** Phase 84 (Spectre/KPTI mitigations),
85 (cross-compiled toolchains), 86 (GitHub integration), 87 (Node.js), 88 (Claude Code),
89 (IPv6 / DHCPv6). They are explicitly framed as 1.x growth, not hidden release debt.

## Release Checklist

A reproducible, off-CI certification a maintainer can run on their own machine — "a gate
only CI can run is theater." Run in order; the env vars turn on every Class (1) opt-in gate.

### 1. Automated gate bundle (copy-pasteable, in order)

```bash
# Class (2) — always-on
cargo xtask check
cargo xtask smoke-test --timeout 300
cargo xtask regression --timeout 90
cargo xtask device-smoke --device nvme
cargo xtask compositor-stress
cargo xtask less-render-probe
cargo xtask session-smoke

# Class (1) — opt-in, enable every M3OS_*_REGRESSION trigger (verbatim from AGENTS.md)
M3OS_E1000_REGRESSION=1            cargo xtask ssh-e1000-banner-check
M3OS_DOOM_AUDIO_REGRESSION=1       cargo xtask doom-audio-smoke
M3OS_TERMIOS_REGRESSION=1          cargo xtask termios-smoke
M3OS_TUI_APP_REGRESSION=1          cargo xtask tui-app-smoke
M3OS_DOOM_CONCURRENT_REGRESSION=1  cargo xtask doom-concurrent-smoke
M3OS_TILING_REGRESSION=1           cargo xtask tiling-smoke

M3OS_USB_REGRESSION=1              cargo xtask xhci-bringup-smoke
M3OS_USB_REGRESSION=1              cargo xtask xhci-enum-smoke
M3OS_USB_REGRESSION=1              cargo xtask usb-smoke
```

### 2. Manual operator checks (once per release-candidate image)

- `cargo xtask run-gui` (or `M3OS_GUI_BACKEND=vnc cargo xtask run-gui` → `vncviewer
  localhost:5900`) and visually confirm the greeter → compositor → `term`/launcher/bar
  session renders.
- SSH in: `ssh -p 2222 root@localhost` — confirm banner + shell prompt.
- Storage round-trip, service lifecycle, `su`/`passwd`, shutdown/reboot — per the Phase 53
  [manual checks](../roadmap/53-headless-hardening.md#gate-bundle).

### 3. PASS verdict the maintainer certifies

> *All Class (2) gates PASS; every Class (1) gate either PASSes with its
> `M3OS_*_REGRESSION` trigger set, or its matrix row is downgraded per the PASS-not-SKIP
> rule. No SKIP is counted as a PASS.*

### 4. Release-notes / CHANGELOG (component-grouped, with Known Issues)

Cut a 1.0 release note grouped by component (kernel, networking, storage, graphical
session, audio, USB, Wi-Fi), each listing the validated `Supported`/`QEMU-validated`
capabilities, plus a **"Known issues"** section drawn directly from
[Non-Goals and Known Limitations](#non-goals-and-known-limitations) (the Redox release-note
shape).

### 5. Reproducible image + known-good / rollback anchor

```bash
cargo xtask image --sign     # builds the signed UEFI image on the recommended config (above)
# Verify the signature, e.g.: sbverify --cert <db.crt> <produced-EFI-binary>
```

Record the exact **commit SHA / git tag** the validated image corresponds to as the
**known-good / rollback anchor** in the release note, so a user can reproduce or roll back
to the exact bits that passed this gate.
